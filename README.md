# Part I template: Application API

A starter for Part I. **New here? Follow [TUTORIAL.md](TUTORIAL.md)** (about an hour): it walks you through the template and then through replacing the example with your own service.

It implements the assignment's running example, a **key-value store**, end to end with dummy responses. **Students do not implement the key-value store:** they replace it with a service of their own and keep the structure.

The structure: **one service, described twice** (OpenAPI for clients, protobuf for servers), with a REST layer that serves every HTTP call by issuing gRPC calls (not necessarily one RPC per REST operation).

```
            REST / JSON                           gRPC / protobuf
client ───────────────────▶  HTTP handlers  ───────────────────▶  KVStore gRPC server
        (api/openapi.yaml)   internal/httpapi   (proto/kvs/v1)    internal/grpcsvc
                             ▲ generated by                       ▲ generated by
                             │ oapi-codegen                       │ protoc
```

In Part I the gRPC server returns **dummy** values. In Part II it applies operations to the state machine; in Part III it submits them to the replicated log. The REST layer stays as it is.

## The five steps

REST side first (steps 1–2), then the gRPC side (steps 3–4), then connect them (step 5).

| # | Step | You edit | Generated / run | Checkpoint |
|---|------|----------|-----------------|------------|
| 1 | Define the service in OpenAPI (Swagger Editor) | `api/openapi.yaml` | – | No errors or warnings in the Swagger Editor |
| 2 | Generate the HTTP server | `api/oapi-codegen.yaml` | `make gen-rest` → `gen/rest/` | Generated code compiles |
| 3 | Define the internal service in protobuf | `proto/kvs/v1/kvs.proto` | – | Every REST operation can be served by the RPCs (not necessarily 1:1); mapping written down |
| 4 | Compile the gRPC service with dummy responses | `internal/grpcsvc/server.go` | `make gen-proto` → `gen/kvs/v1/` | `grpcurl` gets a dummy reply |
| 5 | Implement HTTP handlers by issuing RPCs | `internal/httpapi/handlers.go` | `make run` | `etc/demo.sh` gets the expected status codes, on one node and through a second node |

## The example API

Eight REST operations, served by three RPCs. **POST sets** values; **PATCH modifies** them with a read-modify-write operation.

| Method | Path | Meaning | RPC |
|---|---|---|---|
| `GET` | `/v1/keys` | Read several keys: `?key=` (repeat), `?prefix=` or `?from=&to=`; `?sort=-version`, `?limit=`, `?keysOnly=` | `Read` |
| `POST` | `/v1/keys` | Set several keys atomically (`ifVersion` per key) | `Update` (set) |
| `PATCH` | `/v1/keys` | Append to / increment several keys atomically | `Update` (append, increment) |
| `DELETE` | `/v1/keys?key=` | Delete several keys atomically | `Delete` |
| `GET` | `/v1/keys/{key}` | Read one key; `ETag` = version; 404 if missing | `Read` |
| `POST` | `/v1/keys/{key}` | Set one key: 201 created, 200 replaced; `If-Match` → 412 on mismatch | `Update` (set) |
| `PATCH` | `/v1/keys/{key}` | `{"append":"x"}` or `{"increment":1}` | `Update` (append, increment) |
| `DELETE` | `/v1/keys/{key}` | Delete one key (204) | `Delete` |

Reads take `?consistency=sequential|linearizable`. Errors are `application/problem+json` (RFC 9457). The dummy server pretends the store holds `alpha`, `beta`, `gamma`, all at version 1; the key `missing` never exists.

All eight example operations work end to end. To start your own service, go through the steps in order and replace the example in each file:

| File | Replace |
|---|---|
| `api/openapi.yaml` | the key-value paths and schemas with your service's |
| `proto/kvs/v1/kvs.proto` | the `KVStore` service and messages (rename the package and folder, e.g. `bank/v1`) |
| `internal/grpcsvc/server.go` | the dummy RPC implementations |
| `internal/httpapi/handlers.go` | the handlers (one per `operationId`), conversions and error mapping |
| `etc/demo.sh` | the `curl` calls |

Until a new RPC is written, it answers `UNIMPLEMENTED`, which becomes HTTP 501, so the project keeps compiling while you work.

## Quick start

```sh
# prerequisites: Go >= 1.26, protoc (install: https://protobuf.dev/installation/)
make setup        # once: pins oapi-codegen, protoc-gen-go, protoc-gen-go-grpc in go.mod
make run          # generates, builds, starts node n1 (REST :8080, gRPC :50051)
./etc/demo.sh     # in another terminal

make check        # all in one: generators, build, two nodes, every status code checked

make run2         # node n2 (REST :8081) forwards everything to n1 over gRPC
./etc/demo.sh http://localhost:8081   # values say "from n1"
```

## Editing vs. viewing the API

**Editors:** Swagger Editor, Scalar API Client. **Viewers** (plus test requests): Swagger UI, Scalar API Reference. Docker is optional for all of them.

| Tool | Use it to | Without Docker | Self-hosted (Docker) |
|---|---|---|---|
| **Swagger Editor** | **edit** `api/openapi.yaml` with live errors and preview | `make run` → http://localhost:8080/editor (or https://editor.swagger.io → File → Import file) | `make tools-up` → http://localhost:8090 |
| **Swagger UI** | **view** the API and call it with "Try it out" | `make run` → http://localhost:8080/docs | `make tools-up` → http://localhost:8091 |
| **Scalar API Reference** | **view** the API and call it with "Test Request" (modern alternative to Swagger UI) | – | `make tools-up` → http://localhost:8092 |
| **Scalar API Client** (desktop app) | **edit** the spec and send requests, Postman-style | Install from https://scalar.com/download, import `http://localhost:8080/openapi.yaml` or the file; export to save | – (desktop app, no Docker image) |
| Either Swagger page, server not running | edit / view only | `cd api && python3 -m http.server 8000` → http://localhost:8000/editor.html or `/docs.html` | – |

Notes:
- **No tool writes to your file.** Swagger Editor: File → Save as YAML; Scalar API Client: export. Overwrite `api/openapi.yaml`, then `make gen-rest`. The Scalar desktop app is not a browser, so it needs no CORS setup.
- **`/editor` and `/docs` need no Docker.** Each is one HTML file (`api/editor.html`, `api/docs.html`) embedded in the server, served from the same origin as the API, so "Try it out" needs no CORS setup. They load Swagger from a CDN, so the browser needs internet access. Each node serves its own (`:8081/docs` for n2).
- **The Docker pages run on other ports**, so their "Try it out" / "Test Request" calls are cross-origin. Start the server with `make run CORS='*'` (dev only) and pick the `http://localhost:8080` server in the page's *Servers* drop-down.
- **View-only page:** uncomment `supportedSubmitMethods: []` in `api/docs.html`.

Inspect the gRPC side directly (reflection is on):

```sh
grpcurl -plaintext localhost:50051 list
grpcurl -plaintext -d '{"key":"alpha"}' localhost:50051 kvs.v1.KVStore/Read
grpcurl -plaintext -d '{"prefix":"a","sort":{"descending":true}}' localhost:50051 kvs.v1.KVStore/Read
grpcurl -plaintext -d '{"key":"n","increment":5}' localhost:50051 kvs.v1.KVStore/Update
```

## Layout

```
api/openapi.yaml           step 1: REST API (source of truth for clients)
api/oapi-codegen.yaml      step 2: generator config
api/spec.go, docs.html, editor.html   serve /openapi.yaml, Swagger UI at /docs, Swagger Editor at /editor
docker/api-tools.compose.yaml  optional self-hosted Swagger Editor, Swagger UI, Scalar
proto/kvs/v1/kvs.proto     step 3: gRPC service
internal/grpcsvc/          step 4: gRPC server (dummy in Part I)
internal/httpapi/          step 5: REST handlers -> gRPC client, error mapping
cmd/server/main.go         wires both servers into one process
etc/demo.sh                curl smoke test
etc/check.sh               self-checking end-to-end test (make check)
TUTORIAL.md                step-by-step guide to the template
gen/                       generated code (make gen); do not edit by hand
```

## Rules of thumb

- **Change the spec, then regenerate.** The line `var _ rest.StrictServerInterface = (*Handlers)(nil)` makes the build fail when the handlers stop matching the spec.
- **Map errors in one place.** gRPC status codes become HTTP status codes only in `httpStatusFromGRPC`. They must match the responses documented in `openapi.yaml`.
- **Keep handlers stateless.** All state lives behind the gRPC service.
